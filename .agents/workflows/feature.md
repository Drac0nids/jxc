# 业务开发标准工作流 (Feature Development Workflow)

## 适用范围

**以下两种情况必须执行本工作流，不得跳过：**
1. 用户发出 `/feature` 指令时；
2. 任何涉及"新增功能、修改业务逻辑、改变 UI 交互、新增/修改后端接口"的需求，即使用户没有显式发出 `/feature`。

---

## 执行步骤（单步执行，严禁越步）

### 步骤 1：定位资料

主动读取以下文件，了解现有设计：
- `产品需求文档.md`（PRD）
- `API接口定义文档.md`
- `架构设计文档.md`

### 步骤 2：分析变化范围

梳理本次需求，判断哪些文档需要更新（参考下表）：

| 变动类型 | 需要更新的文档 |
|---|---|
| 新增或修改后端 API 接口（路径/字段/错误码） | ✅ PRD + ✅ API文档 + ✅ 架构文档 |
| 新增或修改业务功能（含纯前端功能） | ✅ PRD + ✅ 架构文档 |
| 数据库表结构变更 | ✅ 架构文档 |
| 仅改 UI 布局/样式/文案，不改业务逻辑 | ✅ PRD（验收标准部分） |
| 仅修改 Bug（不涉及设计变更） | ❌ 无需更新（可在 PRD 备注） |

> **判断原则**：只要"行为语义"变了，就必须更新文档。**不确定时默认更新**。

### 步骤 3：更新版本号

每次更新文档时，将三个文档头部的版本号一并递进：
- 格式：`vX.Y.Z`
- 规则：新增大功能 → `Y+1`；小改动/优化 → `Z+1`

### 步骤 4：强制写入文档

使用代码编辑工具同步更新对应的 `.md` 文档。  
**禁止用文字描述代替实际写入**（如"应该在PRD里加xxx"是不合规的）。

### 步骤 5：中断等待确认

修改完毕后，**必须打断当前的工作流，向 USER 发出明确的询问**：

> "📄 我已更新了以下文档：[列出文件名和版本号]。主要变更如下：[简要说明]。**您确认无误吗？**"

### 步骤 6：进入代码环节

**必须等待 USER 回复通过（如"可以"、"OK"、"没问题"等确认暗示）后**，才能对业务代码文件（`.dart`、`.rs`、`.vue` 等）发起变更。  
**在没有得到 USER 同意前就修改了代码文件，将被视为严重违规。**

---

## 文档补写规则（事后补救）

如果因为沟通节奏原因，代码先于文档更新，则：
1. **立即补写文档**，不得拖延到下一个需求。
2. 补写后主动告知用户："已补更文档第 X.X 节，对应刚才的 [功能名] 变更。"
3. 版本号仍需递进。

---

## 快速判断卡片

```
本次改动是否满足以下任一条？
  ① 新增/修改了 API 路由或字段
  ② 新增了一个页面或功能模块
  ③ 修改了用户可感知的交互行为
  ④ 修改了数据库表结构
  ⑤ 改变了权限矩阵

任意一条为 YES → 必须更新对应文档
全部为 NO  → 可跳过（仅 Bug 修复/重构）
```
